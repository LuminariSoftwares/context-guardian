The architecture, in my words. The proxy is stateless per request. A client (OpenAI chat or Anthropic Messages) resends its
whole history every turn. For each request the proxy estimates tokens (or asks llama.cpp/vLLM to count). Over the budget, it
splits the messages into system, "older" and "recent kept", asks the same backend to summarise "older" (fenced as data,
in pieces if it would not fit), writes the originals plus the summary as a plain-JSON span in a per-run archive folder,
seals the file into a SHA-256 hash chain (`chain.jsonl`), indexes it, and forwards `system + one summary message + recent`.
Failure anywhere forwards the client's own bytes (ADR 0001). The only memory of past compactions is in-process: a summary memo
keyed by hashes of the evicted messages (so the same range is not re-summarised), the calibrator, and a 64-entry session table
for `/guardian/usage`. Spans on disk are the long-term memory; recall (CLI, MCP read-only tools, the FTS index) reads them. The
summary message is `role: system` and starts with `[Context Guardian auto-compaction`. The DSH engine (`engine.js`) is a
separate implementation of the same idea that shares the archive format. The response path is a pass-through stream with a
copy-after-yield tap that learns token ratios from `usage`.

Consequences I am designing around: the proxy cannot "remember" anything about a client between requests except what it
keeps in memory itself; every feature that changes a request must be re-derivable from the history the client resends; response
rewriting has so far never happened, so feature A is the first code that sits in the response path.

Branches: one per item, each from `main`, prefix `claude/steals-`. This log lives on the session branch
`claude/context-guardian-features-599iem`. The README section the brief calls "Credits" is named "Acknowledgements"; the credit
line went there.

### 2026-11-10 ~08:45 CST (approximate): B code review, C and D design reviews came back "revise"

B code review (fresh Opus): one blocker. On the Anthropic route a list-form `system` (the shape Claude Code sends) was estimated
at 0 tokens, so the headline "kept N% of the prefix" was wrong and contradicted itself. Fixed, with proxy-level Anthropic tests (the
unit tests had not reached that path). Also fixed: ledger work ran before the last chunk of the response (reproduced with a 0.5 s
sleep), llama.cpp `cache_n` ignored when `usage` was present, a reused memo with a changed front mislabelled as a replay, stale
"previous request" after a skipped oversized one, misleading wording when a stream carried no usage frame.

C design review (Fable): revise, five design-level blockers in the first draft. The model-written summary would have been a
permanent `system` message with authority (bypassing the fence and the pin logic, and an irreducible floor); the model could fold
turns it could not see (already auto-summarised); hash-tuple matching could hit a repeated run inside the protected window;
"fail open" was not achievable after upstream calls and span writes; the non-streaming loop mishandled `stream_options`,
`tool_choice`, `accept-encoding`. Redesign: the model proposes a turn range only; the proxy's own fenced summariser writes the
summary into the standard summary message; folds apply on the NEXT request, anchored by position and preceding hash chain; pending
folds commit only when the loop finishes. Re-review requested.

D design review (Opus): revise. Real bugs in my design: on POSIX the proxy would have shared the terminal's process group and died
when the user pressed Ctrl-C to cancel a turn in the client; no SIGTERM/SIGHUP handling; port resolution ignored `.env`; loopback
not exempted from `HTTP(S)_PROXY`; the npm wrapper would run the client in the package directory and the bridge's Python lacks
fastapi. All adopted. Re-review requested.
